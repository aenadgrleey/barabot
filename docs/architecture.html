Barabot architecture

This is the agreed design, not implemented yet. We checked DBOS behavior in a spike on DBOS 3.6.0 with SQLite, summarized in "DBOS findings" below.

Diagram

Blue arrows show the notification path. Dashed blue means the step gets the live bot client from bot/runtime.py. The Mini App and the bot call the same functions to write subscriptions, so their arrows merge. Arrows pointing into tables are writes. Arrows from process_listing to tables are reads, except when it writes the version into listings.

Components

Barabot runs in one process on a single asyncio event loop. Three services handle outside traffic, and DBOS runs background processing.

__main__ starts DBOS first, then starts the three services. On shutdown, it stops them in reverse order.

ComponentKindOwns
ScraperServiceServiceTelegram user connection via tgmux or Telethon, event handlers, startup backfill
BotServiceServiceBot API connection, message router, command and agent modes, subscription functions
MiniAppServiceServiceHTTP server for the Telegram Mini App, serving the static page and /api/*
DBOSInfrastructureWorkflow state in its own SQLite database at data/dbos.sqlite. We use SQLite in production too because load is small.
ProcessingDBOS workflows and stepsListing assembly, embeddings, and notification routing

The processor is no longer a service. Its logic now lives in DBOS workflow steps and an embedding queue. The three services never call each other directly. They meet only through DBOS and the database.

Database tables

Application data lives in SQLite at data/barabot.sqlite. DBOS keeps its own system database separate.

TableWritten byRead byWhat each row stores
messagesScraperProcessingOne Telegram message: chat_id, msg_id, grouped_id, sender_id, date, text, media, deleted
listingsScraper writes rev. Processing writes content and version.Processing, botOne listing: key, rev, assembled text and media, content hash, version, removed flag
subscriptionsBotProcessingOne user search subscription
deliveriesBotProcessingWhat the bot sent to a user: listing_key, user_id, version, bot_message_id

Every listing has a stable key. For an album, the key is (chat_id, grouped_id). For a single message, it is (chat_id, msg_id). The key does not depend on which messages of the album are still alive, so deleting the first photo does not move the listing.

Ingesting Telegram events

The scraper writes raw Telegram updates to the database and schedules processing. Live NewMessage, MessageEdited, and MessageDeleted events go through the same handler as startup backfill pages.

  1. Save and bump revision. In one transaction, upsert the row in messages and increment rev on its listing with INSERT INTO listings ... ON CONFLICT DO UPDATE SET rev = rev + 1 RETURNING rev. Delete events carry no grouped_id, so the handler looks up the listing key from the stored message row.
  2. Cancel the previous run. Call await DBOS.cancel_workflow_async("listing:{key}:{rev-1}", cancel_children=True). That flag also cancels any bot.notify runs from the old revision.
  3. Schedule the new run. Call await listings_q.enqueue_async(process_listing, key) with SetWorkflowID("listing:{key}:{rev}") and SetEnqueueOptions(delay_seconds=3).

Steps 2 and 3 work together as a debounce. Every new event cancels the previous run, whether it is still waiting for its 3-second delay or already running, and schedules a new one. For example, a three-photo album bumps the revision to 1, 2, and 3, and only listing:{key}:3 runs.

Why we do not use DBOS Debouncer. In DBOS 3.6.0, it keeps the workflow ID of the first call in a burst and drops the IDs of later calls. The handler would have no way to compute which run to cancel.

Why the ID includes the revision. With the default return-existing policy, DBOS returns the existing workflow for any known ID, even a finished one, and starts nothing new.

Known gaps

  • No cap on wait time. A listing edited continuously is postponed indefinitely. If this shows up in practice, add a first_touched_at cap.
  • Crash between step 1 and step 3. If the process dies before enqueueing, the listing waits for its next event. Startup backfill re-touches recent messages.
  • Deletes in basic groups and private chats. These delete events arrive without a chat ID. Their msg_id is unique per account, so the stored message row still resolves them. tgmux resolves the chat from its own msg_id table and delivers each delete only to the chat owner (branch feat/route-deletes, not merged yet). Deletes of messages tgmux never saw or saw more than 30 days ago are dropped.

Workflow process_listing(key)

This workflow turns saved Telegram messages into a listing, generates its embedding, and decides who should be notified. Each numbered item is a DBOS step. Steps run at least once, so each step is idempotent.

  1. Assemble and hash. Read live rows from messages, join captions in msg_id order, and collect media. Compute the content hash. If the hash has not changed, stop.
  2. Save the new version. Write the new content and increment version using compare-and-set with WHERE version = :seen. If no live rows remain, mark the listing as removed.
  3. Generate embedding. Run embedding as a child workflow on an embedding queue with a concurrency limit. This replaces the old EMBEDDING_CONCURRENCY semaphore. The step uses preemptible=True so cancellation interrupts the API call instead of waiting for it.
  4. Route to subscribers. Read subscriptions and deliveries and compute the event for each affected user. The table below lists all five cases.
  5. Enqueue notifications. Enqueue bot.notify(user, kind, key, version) on notify_queue with workflow ID notify:{key}:{rev}:{user}.

Before steps 3 and 5, which have side effects, the workflow checks that its version is still the latest and exits quietly if not. Cancellation stops a stale run as early as possible. The version check covers what cancellation misses.

The delivery row stays after an unmatched event. If a later version matches again, the user gets an updated event. Whether that should notify the user, since they were last told it no longer matched, is still open.

Workflow bot.notify

This workflow sends or updates one message for one user. It lives in the bot domain, and processing only enqueues it.

  1. Check freshness. Verify that version is still the latest. Exit if not.
  2. Send or edit, and record. Call Telegram and write the row in deliveries inside the same step.

What step 2 sends depends on the event kind:

  • new sends a message.
  • updated silently edits the previously recorded message.
  • unmatched and removed edit that message and tell the user explicitly that the listing no longer matches or was deleted.

Why sending and recording share one step. Cancellation stops a workflow only between steps. If send and write were two steps, cancel_children=True could land after sending and before writing. The next revision would then send the same listing again as new.

Inside one step, a crash between sending and writing can still duplicate a message after recovery. That window is small and acceptable.

The step gets the bot client through bot/runtime.py. BotService.start() stores its client there, and stop() clears it. Nothing outside the bot domain touches this module. If the client is missing, the step raises and DBOS retries it later. The rate limit on notify_queue enforces the Bot API send rate.

User interfaces

Users manage their searches, stored as rows in subscriptions, through three interfaces. The interfaces differ only in how the user expresses intent. All three call the same subscription functions in the bot domain, so validation and side effects live in one place.

InterfaceHow the user worksStatus
Command modeExplicit bot commands to create, list, edit, and delete searchesPlanned
Agent modeFree text to the bot. An LLM agent turns it into calls to the same subscription functions, exposed as tools.Experiment, enabled for part of the users
Mini AppTelegram Mini App with forms for doing the same by handFirst version: read-only list of the user's searches

Chat routing

Command mode and agent mode are two modes of one chat. A router in BotService receives every incoming message and picks the mode per user. Agent mode runs as an experiment. Users in the experiment group go to the agent, and everyone else goes to command mode.

The experiment group is set in BARABOT_AGENT_USERS inside config/.env as a comma-separated list of Telegram user IDs. Agent users get no slash commands. Every message they send goes to the agent.

Telegram Mini App

The Mini App is a web page opened from the bot. MiniAppService runs as a third service in the same TaskGroup and serves the page plus a small HTTP API. The API validates Telegram initData with the bot token to identify the user, then calls the same subscription functions as the chat.

First version scope:

  • GET /api/subscriptions returns the current user's searches.
  • The page renders them as a list, with no editing yet.

DBOS findings

We checked DBOS behavior in a spike before writing production code. Nothing blocks the design. Full report: ~/Dev/agent-home/.experiments/dbos-spike/REPORT.md.

Event loop and async API

  • DBOS.launch() and destroy() are synchronous and work inside the running loop. Async steps run on our loop and do not stall it. A 100 ms heartbeat lagged at most 36 ms normally, and 64 ms under load.
  • From coroutines, use only *_async calls: enqueue_async, cancel_workflow_async, register_queue_async, and get_workflow_status_async. Most sync versions raise inside the loop. Sync enqueue passes, but blocks on SQLite.

Cancellation, workflow IDs, and restarts

  • A delayed enqueue can be cancelled before it starts. A burst of 5 events ran only the last revision.
  • Cancelling a running workflow lets the current step finish and stops before the next one, unless the step has preemptible=True.
  • Cancelling a parent leaves its children alone unless you pass cancel_children=True. With that flag, waiting and running children are cancelled, even when the parent already finished.
  • A known ID returns the existing workflow, including a cancelled one. Every revision needs a new ID, which listing:{key}:{rev} provides.
  • After kill, the workflow resumes at the interrupted step and repeats it in full. Delayed enqueues survive restart.
  • Each cancel of a running workflow logs a WARNING and an ERROR traceback for DBOSAwaitedWorkflowCancelledError. Filter it in the dbos logger.

SQLite and queue throughput

  • No database is locked errors occurred at 50 events/s for 20 s with both databases written. DBOS uses busy_timeout=30000, so contention becomes waiting.
  • A queue with worker_concurrency=1 starts one workflow per poll. notify_queue gets about 14 sends/s at polling_interval_sec=0.05 and 4.6/s at 0.2. 14 sends/s is below the Bot API global limit, so use 0.05.

Not covered by the spike: a real Telethon client, which we simulated with a coroutine, and Python versions other than 3.14.

Open questions

These points still need decisions before implementation.

  • Public URL. Which public HTTPS URL to use for MiniAppService.
  • Message texts. Exact wording for new, unmatched, and removed.
  • Notifying on unmatched and removed. An edit alone triggers no Telegram notification, so this likely needs a reply to the original message.
  • Re-matching after unmatched. Whether a later updated event should notify the user after they were previously told the listing no longer matched.
